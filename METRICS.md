# Метрики логирования JAXGCRL

Документ описывает метрики фактического пути запуска: `train.py` вызывает
`src/make_trains/make_train_several_seeds.py`, где после каждого шага обучения
собирается словарь для Weights & Biases (W&B). `src/logz/logger.py` добавляет к
нему `env_step` и, начиная со второго вызова, `sps`.

Основные метрики отправляются в W&B только при `USE_WANDB=True`. Номер обновления
`update_step` начинается с нуля. В формулах `mean` означает среднее по всем
элементам массива, включая оси эпох и minibatch-ей, если они есть.

## PPO и поведенческое клонирование

Пусть `π_old` — политика, записанная при сборе rollout, `π` — текущая политика,
`A_norm` — нормализованное преимущество, `V` — текущая оценка критика, `V_old` —
оценка при сборе rollout, `R̂` — цель GAE, `ε` — `PPO_CLIP_EPS`.

| Ключ W&B | Что показывает и как вычисляется |
|---|---|
| `total_loss` | Среднее значение полного PPO loss по PPO эпохам и minibatch-ам: `L_actor + PPO_VF_COEF * L_value - PPO_ENT_COEF * H(π) + bc_policy_coef_now * L_BC`. Это именно обучающий loss, а не оценка качества поведения. |
| `actor_loss` | PPO clipped surrogate loss: `-mean(min(r * A_norm, clip(r, 1-ε, 1+ε) * A_norm))`, где `r = exp(log π(a\|s,g) - log π_old(a\|s,g))`. |
| `value_loss` | Clipped value loss. Сначала `V_clip = V_old + clip(V - V_old, -ε, ε)`, затем `0.5 * mean(max((V - R̂)^2, (V_clip - R̂)^2))`. |
| `value_loss_scaled` | `value_loss * PPO_VF_COEF`; вклад value loss в полный PPO loss. |
| `entropy_loss` | Средняя энтропия распределения действий политики `H(π) = -Σ_a π(a) log π(a)`. Несмотря на суффикс `loss`, это положительная энтропия. |
| `entropy_loss_scaled` | `entropy_loss * PPO_ENT_COEF`. Этот член вычитается из `total_loss`, поощряя исследование. |
| `bc_policy_loss` | Потеря клонирования CRL-политики. При `BC_POLICY_TARGET=argmax`: `-mean(log π(a*\|s,g))`, где `a* = argmax_a q(s,a,g)`. При `softmax`: `-mean(Σ_a p_q(a) log π(a\|s,g))`, где `p_q = softmax(q(s,·,g) / BC_POLICY_TEMP)`. Здесь `q` — оценки CRL для командной цели, вычисленные при сборе rollout; градиент через них остановлен. |
| `bc_policy_loss_scaled` | `bc_policy_loss * bc_policy_coef_now`; взвешенный вклад клонирования в `total_loss`. |
| `bc_policy_coef` | Текущее значение коэффициента клонирования. Если включён `ANNEAL_BC`, то `BC_COEF_POLICY * max(0, 1 - update_step / NUM_UPDATES)`, иначе `BC_COEF_POLICY`. |

Каждый из пяти loss-ов PPO (`total_loss`, `actor_loss`, `value_loss`,
`entropy_loss`, `bc_policy_loss`) сначала вычисляется на PPO minibatch-е, затем
`metrics` берёт среднее по результатам всех PPO эпох и minibatch-ей данного
обновления.

## CRL-критик

Для обучающего элемента `i` критик возвращает оценки `q_{i,g}` для взятого
действия и всех `K` целей. К этим логитам код добавляет ещё один фиксированный
логит `0` для поглощающего класса `⊥`. `y_{i,g}` и `y_{i,⊥}` — мягкая целевая
вероятность, сформированная `make_crl_targets`.

| Ключ W&B | Что показывает и как вычисляется |
|---|---|
| `crl_loss` | Средняя полная cross-entropy по CRL эпохам, minibatch-ам и элементам: `-mean_i(Σ_g y_{i,g} log softmax([q_{i,1}, …, q_{i,K}, 0])_g + y_{i,⊥} log softmax([q_{i,1}, …, q_{i,K}, 0])_⊥)`. Это loss классификации распределения будущих целей и поглощающего класса. |
| `crl_scores` | Среднее сырых оценок `q_{i,g}` для действий, которые реально были выбраны в rollout, по CRL эпохам, minibatch-ам, примерам и всем целям. Эти оценки — logits/совместимости CRL, а не калиброванные награды или вероятности успеха. |

Слово `mean` здесь соответствует `.mean()` по массивам, возвращённым CRL
обновлением: для `crl_loss` усредняются скаляры minibatch-ей, для `crl_scores` —
все элементы тензора оценок размера примерно `[CRL_NUM_EPOCHS,
CRL_NUM_MINIBATCHES, CRL_MINIBATCH_SIZE, K]`.

Цель `y` имеет форму `[NUM_STEPS, NUM_ENVS, K + 1]` и строится в
`make_crl_targets`. Для якоря rollout суммируются доступные смещения
`k = 0, …, min(NUM_STEPS, CRL_OFFSET_CAP) - 1`; смещение учитывается, если оно
не выходит за rollout и переходы до него не завершились (`done=False`). Его вес
равен `(1 - GAMMA) * GAMMA**k`. В каждом будущем наблюдении общий вес делится
поровну между всеми достигнутыми целями. Массы реальных целей нормируются на
сумму весов; при заданном `CRL_TERMINATION_DISCOUNT` они дополнительно
умножаются на `1 - δ**d`, где `δ` — этот коэффициент, а `d` — число переходов до
наблюдаемого конца эпизода (если он попал в rollout). Остаток
`1 - sum(y_real_goals)` назначается классу `⊥`. Поэтому `crl_loss` измеряет
cross-entropy именно по такому мягкому распределению.

## Цели и успешность

Пусть `K = num_goals`. Счётчики успехов и неудач имеют форму `[K]`, хранятся
между обновлениями и изначально равны нулю. На обновлении `u` отношение считается
до добавления исходов текущего rollout:

`live_success_rate[g] = success_counter[g] / (success_counter[g] + failure_counter[g] + 1e-7)`.

За текущий rollout успех для командной цели учитывается, если она завершена и
до этого в эпизоде не было завершённых командных целей (`done_goal` и
`num_goals_completed == 0`). Неудача учитывается для командной цели, если эпизод
закончился, а завершённых целей в нём ещё не было (`done_ep` и
`num_goals_completed == 0`). По каждому индексу цели прибавляется число таких
событий. Затем оба вектора счётчиков умножаются на
`LIVE_SUCCESS_RATE_DECAY`. Поэтому это отношение затухающих счётчиков, а не
успешность только последнего rollout. В первом обновлении все отношения равны
нулю; его исходы повлияют на лог следующего обновления.

| Ключ W&B | Что показывает и как вычисляется |
|---|---|
| `live_success_rates_<имя_цели>` | Отношение из формулы выше для одной цели. Отдельные ключи создаются только при `GOAL_SET=semantic`, по одному на каждое значение `all_goal_names`. |
| `live_success_rates_aggregate/all` | Простое среднее `mean(live_success_rates)` по всем `K` целям. Непосещённые цели также входят в среднее со своим текущим значением, обычно нулём. Для `GOAL_SET=observation` это единственный логируемый показатель live success rate; отдельные тысячи ключей признаков не создаются. |
| `goals/num_goals_completed` | Среднее количество завершённых командных целей в эпизодах, завершившихся внутри текущего rollout: `sum(num_goals_completed * done_ep) / max(sum(done_ep), 1)`. Если ни один эпизод не закончился, значение равно нулю. `num_goals_completed` — число завершённых командных целей в эпизоде до текущего перехода. |
| `goals/goals_seen` | Число различных целей, когда-либо отмеченных как увиденные: `sum(goals_seen)`. Булев вектор накапливается через логическое OR для начальных наблюдений сброса и наблюдений текущего rollout. |
| `goals/goals_seen_ratio` | Доля отмеченных целей: `sum(goals_seen) / K`. Диапазон — от 0 до 1 при корректной маске длины `K`. |

## Служебные оси и скорость

`update_step` и `env_step` — индексы для понимания прогресса, а не качества
модели. Пусть `N = NUM_STEPS * NUM_ENVS` — число переходов среды в одном
rollout/update.

| Ключ W&B | Что показывает и как вычисляется |
|---|---|
| `update_step` | Нулевой индекс обновления, сохранённый в training state. Увеличивается на 1 после логируемого шага обучения. |
| `env_step` | Вычисляется в `logger.py`: `NUM_STEPS * NUM_ENVS * int(update_step)`. Так как индекс начинается с нуля и логирование происходит после rollout, на графике это значение отстаёт на один rollout от числа уже собранных переходов: при первом логе оно равно 0. |
| `sps` | Оценка transitions per second, добавляется в `logger.py` начиная со второго вызова логгера: `(NUM_STEPS * NUM_ENVS * config.get("WANDB_LOG_INTERVAL", 1)) / (текущее_время - время_предыдущего_вызова)`. Первый лог не содержит `sps`. В активном CLI `WANDB_LOG_INTERVAL` не объявлен, поэтому используется fallback 1. |

`wandb.log(info)` также ведёт собственный служебный шаг W&B. Он автоматически
создаётся библиотекой и отдельно в коде проекта не рассчитывается.

## Что формируется, но не отправляется как метрика W&B

- `LogWrapper` кладёт в `info` поля `returned_episode_returns`,
  `returned_episode_lengths`, `episode_returns`, `episode_lengths`, `timestep` и
  `returned_episode`. Также rollout добавляет `goals_achieved`. Поле `info`
  сохраняется в `Transition`, но ни одно из этих полей не добавляется в словарь
  `metrics` и не передаётся отдельным вызовом в `wandb.log`.
- При сборке rollout код печатает `ppo loss info` через `jax.debug.print`.
  Это массивы loss-ов PPO до итогового `.mean()` по обновлению, а не отдельные
  метрики с W&B ключами.
- При `USE_WANDB=True` печатается словарь `metrics`. Этот вывод происходит до
  вызова логгера, поэтому в нём нет добавленных логгером `env_step` и `sps`.
- Если `USE_WANDB=False`, словарь W&B метрик не отправляется; безусловный debug
  вывод `ppo loss info` при этом остаётся.

## Где смотреть реализацию

- `train.py` выбирает `make_train_several_seeds.run_dual_crl_ppo`.
- `src/make_trains/make_train_several_seeds.py` обновляет счётчики, вычисляет
  PPO/CRL losses и собирает словарь `metrics`.
- `src/crl_targets.py` формирует мягкие целевые распределения CRL.
- `src/models/crl_models_gc.py` вычисляет оценки CRL и возвращает оценки для
  выбранных действий.
- `src/logz/logger.py` добавляет `env_step` и `sps` и вызывает `wandb.log`.
- `src/wrappers.py` собирает поля эпизодов в `info`, но они не попадают в W&B
  метрики текущего training loop.
